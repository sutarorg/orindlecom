# Technical SEO Audit

**Audited:** 16 November 2026 · **Verdict:** no blocking issues found; three were
found and fixed during the audit.

---

## 1. Canonical domain and host

| Item | State |
| --- | --- |
| Canonical host | `https://orindle.com` — apex, no `www` |
| HTTP → HTTPS | Enforced by HSTS `max-age=63072000; includeSubDomains; preload` |
| `metadataBase` | Set in `src/app/layout.tsx` to the canonical origin |
| Trailing slash | Root resolves to `https://orindle.com` (no slash); all other paths have no trailing slash |
| Redirect chains | None generated by the app. Apex/`www` consolidation must be done at the DNS/host level — see the open items |

`metadataBase` deserves a note. Without it, Next resolves canonical and Open Graph URLs
against whatever host served the request. On a preview deployment that means the
canonical points at a `*.vercel.app` URL and the social card silently breaks. It is set
once, in the root layout, and every page inherits it.

**Verification:** `scripts/seo-audit.mjs` compares every rendered `<link rel="canonical">`
against the expected absolute URL for its route.

## 3. Issues found and fixed during this audit

Three real problems, each of which would have shipped unnoticed.

### 3.1 Homepage canonical lost its trailing slash

**Symptom:** `<link rel="canonical" href="https://orindle.com">` while the sitemap
declared `https://orindle.com/`.

**Cause:** Next's metadata resolver normalises a canonical that equals the origin by
stripping the trailing slash. Declaring `/` as the canonical path produced the bare
origin; the sitemap, built by hand, produced the slash form.

**Fix:** rather than fight the framework, both sides were unified on the bare origin.
`canonicalUrl("/")` returns `https://orindle.com`, the sitemap emits the same string,
and the audit asserts they match exactly. Two forms of one URL across two files is the
kind of inconsistency that makes a "Duplicate, Google chose a different canonical" warning
appear six weeks later.

### 3.2 The audit script assumed image filenames matched slugs

**Symptom:** six false 404s on blog images.

**Cause:** two articles use shorter image names than their slugs
(`how-much-cloud-storage.webp` for `how-much-cloud-storage-do-you-need`), and the
script constructed `/{slug}.webp`. The images were fine; the checker was wrong.

**Fix:** the script now reads each article's `image.src` from the source file. A checker
that guesses is worse than no checker, because it produces confident false alarms.

### 3.3 A comment tripped a source-text assertion

**Symptom:** a test asserting `robots.ts` does not contain `/_next` failed, because the
comment explaining *why* it must not contain `/_next` mentioned `/_next`.

**Fix:** comments are stripped before matching. This is the second time in this codebase
that a regex over source text matched its own documentation; the pattern is now explicit
in the test and in the code that reads it.

## 4. Indexability

### Public (indexable, in sitemap) — 26 URLs

`/`, `/pricing`, `/features`, `/security`, `/teams`, `/about`, `/contact`, `/faq`,
`/help`, `/legal`, `/privacy`, `/terms`, `/cookies`, `/acceptable-use`, `/data-deletion`,
`/blog`, plus the ten `/blog/{slug}` articles.

### Private (excluded by three layers)

| Layer | Mechanism | What it stops |
| --- | --- | --- |
| 1 | `robots.txt` disallow | Discovery |
| 2 | `noindex, nofollow` meta | Indexing a URL known from elsewhere |
| 3 | Middleware session gate + RLS | The content existing for an unauthorised caller |

Routes: `/dashboard/*`, `/account`, `/login`, `/signup`, `/sign-in`, `/sign-up`,
`/forgot-password`, `/reset-password`, `/verify-email`, `/auth/*`, `/api/*`.

The audit confirmed `noindex` is present on all four of `/login`, `/signup`,
`/forgot-password` and `/reset-password`.

**A point worth stating:** robots.txt alone does not remove a URL from results. A page
already indexed stays indexed after being disallowed, because the crawler cannot fetch it
to see the noindex. The combination is the only reliable approach, and it is what is
implemented.

## 5. Sitemap

| Item | State |
| --- | --- |
| URL | `https://orindle.com/sitemap.xml` |
| Generated by | `src/app/sitemap.ts`, from `INDEXABLE_PAGES` + `BLOG_ARTICLES` |
| URLs | 26 |
| `lastmod` | Real dates: article `updated` values for articles; fixed revision dates for static pages |
| `changefreq` / `priority` | Present, ignored by Google, set for humans |
| Private URLs included | None — asserted by the audit |
| Draft articles included | None — publishing is controlled by array membership |

**On `lastmod`:** the previous implementation used `new Date()` at request time, which
told Google every URL changed on every crawl. That teaches a crawler to distrust the
field, and it is worse than omitting it. Every entry now carries a date that reflects a
real change.

## 6. robots.txt

```
User-Agent: *
Allow: /
Disallow: /dashboard, /dashboard/, /account, /api/,
          /login, /signup, /sign-in, /sign-up,
          /forgot-password, /reset-password, /verify-email, /auth/
Sitemap: https://orindle.com/sitemap.xml
Host: https://orindle.com
```

Explicit `Allow: /` with a narrow disallow list, rather than the more common
`Disallow: /` plus exceptions — which is easy to get wrong and fails closed.

**Verified absent:** any disallow of `/_next/`, `/images/`, `/fonts/` or `/art/`.
Blocking the asset directory is the single most common self-inflicted technical SEO
wound: Google cannot render the page, so it indexes the fragments. The audit asserts
these are not present.

## 7. Structured data

| Type | Where | Source |
| --- | --- | --- |
| `WebSite` | Homepage | `src/app/page.tsx` |
| `Organization` | Homepage | `src/app/page.tsx` |
| `BlogPosting` | Each article | `src/app/blog/[slug]/page.tsx` |
| `BreadcrumbList` | Each article | `src/app/blog/[slug]/page.tsx` |

Every property is verifiable and none is invented:
- `Organization` has name, URL, logo (a file that exists), and the published support
  address. It has **no** registration number, address or founding date, because those
  do not exist to state.
- `BlogPosting` has headline, description, datePublished, dateModified, image, author
  and publisher. The author is the organisation, which is accurate — there is no
  individual byline to invent.
- **No `aggregateRating`**, no `review`, no `FAQPage`. Ratings that do not exist and FAQ
  markup Google restricts to government and health sites would both be a liability.

Mobile-first is satisfied structurally rather than by assertion: the visual gate renders
